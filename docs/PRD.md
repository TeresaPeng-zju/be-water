# BeWater 产品需求文档（PRD）

> 版本：v0.2  
> 状态：产品方向重构稿  
> 日期：2026-07-17  
> 第一阶段范围：服务管理 → 客户跟进 → 排期与交付 → 反馈采集 → 经营诊断 → 流程沉淀

---

## 1. 产品概述

### 1.1 产品名称

**BeWater**

### 1.2 一句话定位

**BeWater 是面向个体服务者和小型专业团队的个人经营平台，帮助用户管理客户、订单、排期与交付，发现获客和成交过程中的问题，并把反复发生的经验沉淀为可复用的流程、知识和产品。**

### 1.3 产品愿景

让一个已经开始提供专业服务的个体经营者，可以在一个平台中完成：

```text
发布内容
→ 获得线索
→ 沟通需求
→ 报价与成交
→ 安排排期
→ 完成交付
→ 收集反馈
→ 复购与转介绍
→ 复盘经营问题
→ 优化工作流程
→ 沉淀知识资产
→ 形成新的产品
```

随着使用时间增加，BeWater 应越来越理解：

- 用户适合服务哪些客户；
- 用户在什么情况下容易成交；
- 哪些订单会造成较大压力；
- 用户真实的产能和交付节奏；
- 哪些流程正在重复消耗时间；
- 哪些服务值得涨价、拆分或标准化；
- 哪些经验已经可以从一对一服务转化为模板、知识包、课程或其他产品。

### 1.4 核心价值

BeWater 不替用户“自动创业”，也不只是生成内容。它帮助用户回答长期经营中的实际问题：

- 我现在还能不能接新订单？
- 为什么最近咨询很多，却没有成交？
- 为什么有的客户复购，有的客户交付后没有反馈？
- 客户没有执行建议，是不满意，还是存在其他阻碍？
- 哪些客户总在流失，流失发生在哪一步？
- 哪些工作一直重复，可以整理成模板或标准流程？
- 哪些内部经验已经可以成为新的付费产品？
- 我什么时候具备涨价条件？
- 下一步最值得优化的是获客、沟通、交付，还是回访？

BeWater 的核心不是替用户得出一个看似正确的答案，而是把散落在微信、日历、备忘录和表格中的经营信息组织起来，让用户逐渐看清自己的业务。

## 2. 产品背景

### 2.1 真实用户状态

第一目标用户不是完全没有收入来源的创业新手。他们通常已经：

- 有明确的专业能力；
- 通过朋友介绍、社交平台或个人内容获得过客户；
- 完成过一到多次付费服务；
- 能够独立完成交付；
- 相信自己的服务具有价值。

但其经营仍然高度依赖个人感觉：

- 有时连续成交，有时很久没有订单；
- 不知道哪篇内容真正带来了客户；
- 咨询、报价、交付和反馈散落在多个工具中；
- 无法判断当前排期是否还能接新单；
- 急单需求与个人时间、状态经常冲突；
- 不知道流失是因为价格、交期、信任还是需求不匹配；
- 客户交付后没有反馈，不知道是否满意和是否行动；
- 有人复购，却不知道复购发生的原因；
- 做了大量重复工作，却没有形成稳定流程；
- 服务质量不错，但没有依据决定是否涨价；
- 想把经验做成产品，却不知道哪些内容真正具有市场价值。

### 2.2 当前替代方案

用户通常使用：

```text
微信
+ 苹果日历
+ 备忘录
+ Excel / Notion
+ 问卷星
+ 收款码
+ 通用大模型
```

单个工具能完成局部任务，但数据没有连接：

- 日历知道周三有任务，但不知道订单是否赚钱；
- 微信知道客户说过什么，但不知道其成交阶段；
- 表格知道收入，但不知道实际投入时间；
- 通用大模型可以建议涨价，但不了解复购、满意度和产能；
- Notion 可以保存 SOP，但不会主动发现哪些动作已经重复发生。

BeWater 最大的竞争对象不是某一款 CRM，而是用户的习惯：

> “我先凑合用这些工具。”

### 2.3 核心问题

个人服务者缺少的是：

> 一个能够持续记录经营过程、识别重复模式、指出关键瓶颈，并帮助其将经验转化为经营资产的长期系统。

## 3. 产品定位与边界

### 3.1 产品是什么

BeWater 由三部分构成：

#### A. 经营工作台

承载客户、订单、服务、排期、交付、反馈和收入等真实业务对象。

#### B. 经营诊断系统

从长期数据中发现获客、成交、排期、交付和客户关系中的异常与模式。

#### C. 资产沉淀系统

将经营中反复出现的问题和动作，逐步整理为问卷、清单、模板、SOP、知识条目和新产品。

### 3.2 产品不是什么

BeWater 不是：

- 通用聊天机器人；
- AI 内容生成器；
- 从零寻找职业方向的能力测评工具；
- 传统企业 CRM；
- 单纯的日历或任务管理工具；
- 自动批量私信的营销工具；
- 只展示收入和成交率的数据仪表盘；
- 自动替用户决定接单、定价和拒绝客户的系统。

### 3.3 核心承诺

BeWater 不承诺用户一定获得更多订单或一定能够涨价。它应帮助用户：

1. 更清楚地知道业务正在发生什么；
2. 更早发现经营流程中的问题；
3. 减少因排期、沟通和交付混乱造成的客户流失；
4. 更有依据地调整内容、服务、价格和交付方式；
5. 将重复劳动逐渐转化为稳定流程和可复用资产。

### 3.4 产品心智

对外不优先使用“CRM”，建议表达为：

- **个人经营工作台**；
- **个体服务者的经营搭档**。

BeWater 的核心心智是三个动作：

```text
发现：最近 6 个咨询中，4 个因为交期没有成交
验证：未来两周测试每周一个急单名额和 50% 加价
沉淀：把急单反复收集的信息形成问卷和检查清单
```

即：

```text
经营事实 → 经营判断 → 小实验 → 流程资产
```

## 4. 竞品与市场空位

### 4.1 竞品分层

| 类型 | 代表产品 | 主要价值 | BeWater 需要学习 | BeWater 不正面竞争的部分 |
|---|---|---|---|---|
| 自由职业经营工具 | Moxie、Harlow | 客户、项目、时间、财务、带宽 | 轻量一体化与个人产能 | 首版完整财务、合同、支付 |
| 客户流程平台 | HoneyBook、Dubsado | 询价到付款的标准流程和自动化 | 客户生命周期与流程体验 | 复杂自动化、门户、电子签 |
| 垂直客户管理 | CoCoach 等 | 客户参与和服务进展 | 关注客户是否行动和获得结果 | 深度垂直行业全功能 |
| 中国交易平台 | 有赞 | 预约、订单、排班、支付、会员 | 微信生态与预约习惯 | 门店、多员工、标准资源排班 |
| 知识付费平台 | 小鹅通 | 已成型知识产品的销售与交付 | 产品化后的承接链路 | 课程商城和内容交付基础设施 |
| 工具组合 | 微信+日历+表格+大模型 | 灵活、熟悉、低迁移成本 | 极低记录成本 | 继续容忍数据割裂 |

### 4.2 最接近的竞品：Moxie

Moxie 面向自由职业者和个体经营者，将客户、项目、沟通、时间、发票和带宽规划放在一个系统中。其公开介绍明确强调 bandwidth forecasting、客户/项目健康和时间记录，是 BeWater 必须重点研究的产品。[Moxie 客户管理](https://www.withmoxie.com/product-pages/client-management-for-freelancers)、[Moxie 产品总览](https://www.withmoxie.com/product)

Moxie 证明：

1. 个体经营者需要独立于企业 CRM 的管理工具；
2. 客户、项目、时间和财务应该连接；
3. “我还能不能接单”是核心需求。

BeWater 不能只宣传“管理自由职业业务”，而应进一步解决：

- 为什么客户没有成交；
- 为什么客户交付后没有执行；
- 哪些客户容易复购；
- 哪个环节造成持续流失；
- 哪些重复动作值得沉淀；
- 哪些内部经验可以变成新产品。

### 4.3 HoneyBook 与 Dubsado 的启示

[HoneyBook](https://www.honeybook.com/crm-for-freelancers) 强调 clientflow，覆盖咨询、预约、报价、合同、付款和项目推进；[Dubsado](https://www.dubsado.com/pricing) 更强调用户先配置标准流程，再让系统自动执行。

两者说明完整客户流程很有价值，但也会快速膨胀到：

- 合同；
- 支付；
- 邮件；
- 客户门户；
- 自动工作流；
- 企业权限。

BeWater 首版不跟随补齐全部能力。核心差异是：

> Dubsado 帮用户执行已经知道的流程；BeWater 帮用户发现自己应该建立什么流程。

### 4.4 有赞与小鹅通的启示

有赞的预约与排班适合“多个标准项目 + 标准时间段 + 多员工”的业务。[有赞排班管理](https://help.youzan.com/displaylist/detail_53_53-2-281109)

BeWater 服务的是：

```text
一个人
+ 非标准专业服务
+ 隐性准备工作
+ 高度依赖个人判断
+ 交付后的客户行动与结果
```

小鹅通擅长“已有知识产品 → 上架 → 推广 → 成交 → 交付”。BeWater 更关注产品化之前：

```text
每天重复什么
→ 哪些方法产生真实结果
→ 什么可以标准化
→ 是否值得成为知识产品
```

两者更可能是上下游，而不是完全正面竞争。

### 4.5 BeWater 的市场空位

```text
第一层：把业务管起来
客户、订单、排期、交付、反馈

第二层：把业务看明白
成交、流失、产能、客户行动与优先瓶颈

第三层：把经验放大
重复问题 → 清单 → 流程 → SOP → 知识 → 产品
```

市场空位不是“更轻的 CRM”或“带 AI 的 HoneyBook”，而是：

> **帮助个体服务者从自己的经营过程里发现问题、改善流程，并把经验沉淀成资产。**

### 4.6 竞争策略

- 基础经营链路必须真正可用，不能只有 AI 诊断；
- 不正面建设合同、支付、完整邮件和复杂自动化；
- 首版打一个高辨识度垂直场景；
- AI 洞察必须有样本量和具体业务证据；
- 记录必须嵌入自然工作流，而不是要求用户“为了训练 AI”填报表；
- 体验必须比复杂 CRM 更轻，不能因 AI 变得更难使用。

## 5. 目标用户

### 5.1 第一目标用户

已经开始提供专业服务，但尚未形成稳定经营系统的个体服务者。

典型类型：

- 简历修改与求职辅导；
- 模拟面试与职业咨询；
- 设计、开发和产品咨询；
- 健身、营养和健康指导；
- 摄影、剪辑和内容服务；
- 语言教学和一对一辅导；
- 独立顾问和自由职业者；
- 不超过 5 人的专业服务团队。

### 5.2 首版垂直切入

建议首批种子用户聚焦：

> **简历修改、求职辅导和一对一专业咨询服务者。**

原因：

- 创始人有真实业务经验；
- 订单流程清晰但存在大量非标准工作；
- 急单、交期、信息收集和反馈问题明显；
- 容易观察从重复服务到模板、资料包和知识产品的演化；
- 更容易定义准确的字段、状态和首批洞察规则。

### 5.3 用户准入特征

第一阶段优先服务满足至少两项的用户：

- 已完成过至少一笔付费服务；
- 已有明确可售卖的服务；
- 已通过内容、转介绍或社群获得过咨询；
- 正使用日历、微信、备忘录或表格管理订单；
- 已遇到排期、反馈、复购、定价或流失问题。

### 5.4 暂非第一目标用户

- 尚未形成任何服务能力或产品方向的用户；
- 主要经营标准化实体商品的商家；
- 需要大型企业 CRM、复杂财务和组织权限的团队；
- 需要自动广告投放、外呼或批量营销的团队；
- 只想批量生成内容、不愿记录经营结果的用户。

## 6. 产品原则

1. **真实经营优先于 AI 展示**：客户、订单、时间、交付和反馈是主角。
2. **记录来自自然工作流**：在推进业务时自然产生数据，不额外填写经营日报。
3. **先观察，再判断，最后建议**：区分事实、可能原因、未知信息和小实验。
4. **建议必须可追溯**：每条观察链接到相关客户、订单和事件。
5. **人拥有最终决定权**：系统不自动拒单、改价或联系客户。
6. **一次只优化一个问题**：每个周期只指出一个最值得处理的瓶颈。
7. **失败和流失也是数据**：未成交、未行动、无反馈和取消都必须保留。
8. **资产从真实业务中生长**：重复出现且经验证后，才提示标准化和产品化。
9. **确定性逻辑优先**：计算和状态判断不用大模型猜测。
10. **保留人味**：系统像熟悉用户工作方式的经营搭档，不使用空洞 AI 术语。

## 7. 核心经营循环

### 7.1 经营优化循环

```text
内容与渠道
→ 线索
→ 需求沟通
→ 报价
→ 成交
→ 排期
→ 交付
→ 反馈
→ 复购与转介绍
→ 经营复盘
```

系统需要帮助识别：

- 流量或咨询是否减少；
- 咨询后是否没有成交；
- 流失是否集中发生在报价或交期；
- 是否存在超出产能的接单；
- 客户是否完成服务后的行动；
- 满意客户是否被沉淀为案例、复购或转介绍。

### 7.2 资产沉淀循环

```text
重复需求
→ 重复问题
→ 标准信息收集
→ 工作清单
→ 服务 SOP
→ 模板与知识
→ 产品化
→ 新收入来源
```

系统需要帮助识别：

- 哪些问题被反复询问；
- 哪些信息每次都要重新收集；
- 哪些步骤重复消耗时间；
- 哪些材料多次复用；
- 哪些方法已经被多个客户验证；
- 哪些一对一内容可以转化为自助产品；
- 哪些内部知识可以反向成为获客内容。

## 8. MVP 目标与黄金路径

### 8.1 核心目标

让一名已经开始接单的个体服务者，可以在 BeWater 中建立当前服务和最近订单，管理未来排期，完成一次客户交付与回访，并获得第一条基于真实业务数据的经营观察。

### 8.2 第一条真实闭环

```text
创建一个服务
→ 导入或录入三个真实咨询/订单
→ 将一个订单排入本周
→ 完成一次交付
→ 发起一次回访
→ 记录客户反馈
→ 获得一条有依据的经营观察
→ 将一个重复动作保存为清单
```

### 8.3 7 天成功体验

用户在首次使用后的 7 天内能够：

- 建立至少一个当前服务；
- 录入或创建至少三个客户/订单记录；
- 在排期中看到真实产能占用；
- 完成至少一次订单状态流转；
- 完成至少一次轻量回访；
- 看到至少一条有依据的经营观察；
- 选择一个需要优化的问题；
- 将至少一个重复动作保存为流程步骤、清单或模板草稿。

### 8.4 第一阶段不做

- 自动读取完整微信聊天；
- 自动向客户发送营销私信；
- 自动发布社交媒体；
- 复杂财务和税务管理；
- 合同与支付系统；
- 完整邮件和客户门户；
- 大型团队权限；
- 自动替用户定价或接单；
- 完整知识库市场；
- 多 Agent 协作展示；
- 复杂内容生成工作台；
- 无依据的行业对标；
- 以聊天机器人作为主页。

## 9. 核心业务对象

### 9.1 服务（Service）

用户当前对外提供的服务。

关键字段：

- 名称和说明；
- 目标客户；
- 当前价格；
- 标准交期；
- 是否支持急单及急单规则；
- 准备、沟通、交付和修改预计时间；
- 修改次数；
- 包含与不包含的内容；
- 下单前需要收集的信息；
- 状态。

### 9.2 线索（Lead）

对服务表达兴趣但尚未成交的人。

关键字段：

- 姓名或昵称；
- 来源渠道和来源内容；
- 首次咨询时间；
- 感兴趣的服务；
- 需求摘要；
- 期望交期；
- 预算；
- 当前阶段；
- 下一步动作；
- 未成交原因；
- 最近联系时间；
- 是否允许后续跟进。

### 9.3 客户（Customer）

已经成交或完成过服务的人。

关键字段：

- 基础信息；
- 历史订单；
- 沟通偏好；
- 服务反馈；
- 是否复购或转介绍；
- 是否同意作为案例；
- 重要历史说明。

### 9.4 订单（Order）

一次具体的付费服务。

正常状态：

```text
待确认需求 → 待报价 → 待付款 → 已成交
→ 待开始 → 进行中 → 待客户反馈 → 已完成 → 已复购
```

异常状态：

```text
已流失 / 已取消 / 已退款 / 已暂停 / 超期
```

关键字段：

- 客户与服务；
- 实际价格；
- 来源渠道；
- 紧急程度；
- 承诺与实际交付时间；
- 预计与实际工作量；
- 需求和服务边界；
- 交付材料；
- 修改记录；
- 客户反馈与行动状态；
- 复购、转介绍、取消或流失原因。

### 9.5 排期（Schedule）

排期不是普通日历事件，而是连接订单、服务和工作量的经营对象。

时间块类型：

- 客户沟通；
- 准备工作；
- 正式服务；
- 交付制作；
- 修改时间；
- 回访；
- 内容创作；
- 不可工作时间；
- 缓冲时间。

### 9.6 反馈（Feedback）

反馈不只使用星级评分，应覆盖：

- 客户是否满意结果；
- 是否理解交付内容；
- 是否采取建议；
- 哪部分帮助最大；
- 哪部分仍有困难；
- 是否愿意复购、推荐或授权案例；
- 无反馈的原因是否已知。

### 9.7 经营观察（Insight）

一条经营观察必须包括：

- 观察到的事实；
- 时间范围；
- 涉及的业务对象；
- 样本量和证据强度；
- 可能原因；
- 尚未掌握的信息；
- 建议验证的下一步；
- 用户是否采纳；
- 后续结果。

### 9.8 经营实验（Experiment）

用于验证洞察中的假设，包含：

- 来源洞察；
- 假设；
- 准备改变什么；
- 成功标准；
- 开始与结束时间；
- 结果；
- 结论和后续动作。

### 9.9 经营资产（Asset）

从真实工作中沉淀的可复用内容：

- 下单前问卷；
- 客户筛选清单；
- 服务准备清单；
- 沟通提纲；
- 交付 SOP；
- 回访模板；
- 常见问题；
- 示例库和案例；
- 知识条目；
- 自助资料包；
- 可售卖的小产品草稿。

### 9.10 经营事件（Activity Event）

系统以事件记录业务变化：

```text
新线索 / 阶段变化 / 报价 / 成交 / 取消
排期 / 开始交付 / 完成交付 / 回访 / 反馈
复购 / 转介绍 / 流程使用 / 资产创建
```

事件用于审计、恢复、漏斗计算、模式发现和长期记忆来源追踪。

## 10. MVP 信息架构与核心页面

一级导航：

```text
今日 / 客户 / 订单 / 排期 / 复盘 / 资产
```

Bee 不作为一级导航，也不设置独立 AI 聊天主页。

### 10.1 今日经营首页

展示：

- 本周新线索；
- 待跟进客户；
- 进行中订单；
- 本周可用产能；
- 即将到期交付；
- 待回访客户；
- 一个主要经营重点。

快捷动作：

- 记录新咨询；
- 创建订单；
- 安排交付；
- 标记已完成；
- 发起回访；
- 记录经营情况。

### 10.2 客户与线索看板

默认阶段：

```text
新咨询 → 需求确认 → 已报价 → 待付款
→ 已成交 → 交付中 → 待回访 → 已完成
```

每张卡显示：客户、服务、来源、金额、期望交期、最近动作、下一步和风险。

### 10.3 排期与产能页面

提供周视图，首版可暂缓月视图。每个订单可按服务预估拆分为：

- 准备；
- 沟通；
- 交付；
- 修改缓冲；
- 回访。

页面显示：

- 本周总可用时间；
- 已占用和剩余时间；
- 高压力日期；
- 缓冲时间；
- 当前最多可新增订单数；
- 新订单插入后的影响。

系统提供判断依据，不替用户作出接单决定。

### 10.4 订单工作区

包含：需求、交付目标、截止时间、服务边界、进度、待办、材料、沟通摘要、修改次数、实际投入和回访。

订单关闭时使用一个轻量问题补齐状态：

```text
这次服务结果如何？

[顺利完成]
[完成，但过程比较辛苦]
[客户没有执行建议]
[客户反馈不明确]
[产生了额外修改]
[退款或中止]
```

### 10.5 回访中心

第一阶段生成可复制文本，不自动发送。

系统区分：

- 未发起回访；
- 已发送但未回复；
- 回复模糊；
- 明确不满意；
- 满意但尚未行动；
- 已行动但尚无结果；
- 已获得结果。

### 10.6 经营复盘

按环节展示：

- 获客；
- 咨询；
- 成交；
- 排期；
- 交付；
- 客户成功；
- 复购与转介绍；
- 资产沉淀。

不使用单一综合分数。每个环节展示已知事实、数据是否充分、最近变化、可能问题和一个建议实验。

### 10.7 流程与资产

系统先提出候选，不直接自动创建知识库：

> 最近 5 个简历订单中，你都询问了目标岗位、投递时间、原简历和项目成果。需要保存为“简历修改下单前信息清单”吗？

用户确认后创建清单或流程。多次使用后，再建议补充示例、判断规则、自助填写页或产品化草稿。

## 11. Bee 的产品角色

### 11.1 品牌与 Icon

产品名称为 **BeWater**。陪伴角色名为 **Bee**，视觉由“小蜜蜂 + 水滴”构成，对应 `BeeWater` 的谐音彩蛋。

```text
BeWater = 个人经营系统
Bee     = 长期观察经营过程的业务搭档
```

Icon 应将蜜蜂和水滴融合为一个符号，例如水滴形翅膀或由飞行轨迹汇入水滴；避免简单并排和传统大面积黄黑卡通风格。

### 11.2 Bee 的职责

- 在恰当时机指出值得注意的变化；
- 帮助补齐缺失信息；
- 连接散落的经营记录；
- 提出有依据的假设；
- 帮助设计小范围验证；
- 在重复工作出现时提醒沉淀流程；
- 数据不足时明确表达不确定性。

### 11.3 语言原则

建议：

> 最近三个客户都在交付前临时补充需求。可能是下单前信息没有收全。要不要把这些问题加入下单清单？

不建议：

> AI 检测到您的服务流程存在信息采集漏洞，建议一键生成智能 SOP。

Bee 应温暖、诚实、有依据，不卖萌、不泛化鼓励、不制造虚假精确概率。

### 11.4 出现时机

Bee 适合在：

- 新订单可能超过产能；
- 某阶段连续流失；
- 多个客户提出相似需求；
- 多次重复同一工作；
- 订单完成但长期无反馈；
- 价格实验获得初步结果；
- 流程具备资产化条件；
- 用户进行周复盘。

Bee 不应每次页面切换都说话，也不应为了展示 AI 频繁总结。

## 12. 经营诊断框架

### 12.1 获客诊断

关注内容带来的咨询、渠道来源、咨询质量、有效线索率和渠道依赖，不只看浏览和点赞。

### 12.2 成交诊断

关注咨询到报价、报价到付款、决策周期、异议、流失阶段、交期和价格影响。

### 12.3 产能诊断

关注可用时间、实际工作时间、服务平均耗时、沟通和修改隐性时间、超期、急单和因排期造成的流失。

### 12.4 交付诊断

关注预计与实际耗时、临时需求、修改轮次、服务边界、客户理解与行动、用户本人压力最大的环节。

### 12.5 客户成功诊断

关注回访、客户行动、满意反馈、未解决问题、复购、转介绍和案例授权。无反馈不能默认满意。

### 12.6 定价诊断

不只参考市场均价，而应综合需求、成交、产能、满意度、复购、交付结果、实际投入和历史价格实验。

## 13. 首批五类经营洞察

首版只实现五类，避免泛化 AI 分析。

### 13.1 排期即将超载

**主要使用确定性规则。**

触发输入：可用时间、已排时间、缓冲、订单截止日期和服务预计耗时。

输出示例：

> 本周还有 6 小时可用时间，但已安排 5.5 小时，且周四前没有修改缓冲。新增一个标准订单可能导致现有订单超期。

### 13.2 多名客户因交期流失

触发条件初稿：指定时间窗口内，至少 3 条线索标记交期相关流失，且占已知流失原因的显著比例。

输出必须说明样本量，不直接断言因果。建议实验可以是预留急单名额或测试急单加价。

### 13.3 报价后集中流失

触发输入：阶段事件、报价、后续结果、流失原因和决策周期。

系统区分：

- 已知价格问题；
- 报价后未回复；
- 服务不匹配；
- 信息不足，尚无法判断。

### 13.4 订单完成但长期无反馈

规则区分未回访、已发送未回复、模糊回复、满意未行动和明确不满意，不将沉默视为满意。

### 13.5 同一问题或步骤重复出现

触发来源：订单需求、沟通摘要、清单、反馈、重复发送材料和用户明确标记。

满足重复阈值后，AI 可以整理为候选问卷、清单或 SOP，但必须由用户确认后保存。

### 13.6 洞察输出协议

每条洞察必须包含：

```text
观察到的事实
样本与时间范围
证据对象链接
可能原因
未知信息
建议验证的小实验
用户反馈
后续结果
```

## 14. 从工作流到新产品

### 14.1 候选资产识别条件

满足以下任一组合时才提示：

- 同一问题至少出现 3 次；
- 同一步骤至少在 3 个订单中重复；
- 相同材料被多次发送；
- 同类客户存在稳定前置需求；
- 某方法已在多个客户中产生正向结果；
- 某部分交付不依赖大量个性化判断；
- 用户明确标记该环节重复或耗时。

### 14.2 资产成熟度

```text
L1 个人备忘
准备清单、沟通提醒、常见问题

L2 内部流程
下单问卷、交付步骤、回访流程、质检清单

L3 客户自助材料
填写指南、准备手册、服务说明

L4 可售卖产品
自查模板、知识包、准备清单、小型工作坊
```

### 14.3 产品化前提

系统不能因材料多就判断可以售卖。产品化前必须确认：

- 客户是否反复需要；
- 材料是否产生过真实帮助；
- 是否能明确说明价值和边界；
- 是否能与当前服务形成合理关系；
- 是否损害高价服务价值；
- 是否仍需要用户大量个性化判断。

## 15. 数据采集原则

### 15.1 最小记录成本

优先通过自然动作产生数据：

- 创建线索；
- 修改阶段；
- 创建订单；
- 安排排期；
- 标记交付；
- 记录流失原因；
- 发起回访；
- 记录反馈；
- 完成周复盘。

避免每日经营日报。

### 15.2 单问题补充

缺少关键判断信息时，只问一个具体问题：

```text
这位客户没有成交，最接近哪种情况？

[交期不合适]
[价格超出预算]
[暂时不需要]
[选择了其他服务]
[没有继续回复]
[不清楚]
```

### 15.3 历史数据初始化

首版支持用户手动快速录入最近 3–5 个历史咨询或订单。只要求完成当前诊断所需的最小字段，不强迫补齐完整档案。

### 15.4 用户控制

用户可以编辑、删除、导出业务数据；纠正 AI 推断；将信息排除出 AI 分析；删除单条记录或全部个人数据。

## 16. AI、长期记忆与上下文

### 16.1 AI 使用边界

确定性逻辑优先用于：

- 排期冲突；
- 产能计算；
- 订单状态；
- 待办和超期；
- 转化率；
- 价格和收入；
- 剩余名额；
- 固定流程执行。

AI 主要用于：

- 非结构化信息提取；
- 客户反馈总结；
- 重复模式候选发现；
- 可能原因分析；
- 流程草稿；
- 复盘辅助；
- 个性化建议表达。

### 16.2 长期记忆对象

长期记忆围绕经营事实，而不是保存所有聊天文本：

- 服务设置和用户产能；
- 订单、客户阶段和流失原因；
- 反馈、复购和转介绍；
- 用户采纳或拒绝的建议；
- 经营实验和结果；
- 已验证流程；
- 用户明确不接受的经营方式。

事实状态：

```text
observed / confirmed / inferred / rejected / superseded / expired
```

### 16.3 三层上下文架构

参考 Claude Code 的应用层思路，BeWater 区分：

```text
当前请求上下文
模型本轮需要看到的系统规则、业务状态、相关历史和当前输入

可恢复会话记录
完整消息与工具事件，用于恢复、追溯和压缩，不会每轮全部发送

跨会话长期记忆
经过状态管理的服务设置、经营事实、用户决定和历史结果
```

长期连续性来自“模型上下文 + 持久化事件 + 摘要压缩 + 关键状态重注入”，不是模型参数持续学习。

### 16.4 DeepSeek 源码参考边界

本地 DeepSeek-V3 Demo 可借鉴：

- role-based messages；
- 模型 Chat Template；
- Prompt Token 预检；
- 输出 Token 预留；
- 单次生成中的增量推理。

不可将以下内容误认为长期记忆：

- 进程内 `messages`；
- `persistent=False` 的 KV/MLA Cache；
- 长上下文窗口；
- DeepSeek API 的短期 Context Cache。

KV Cache 解决推理性能，BeWater Memory Store 解决跨会话业务状态。

### 16.5 Compact 与关键状态重注入

上下文接近阈值时：

```text
旧会话
→ 结构化摘要
→ 写入 compact boundary
→ 用摘要替换旧活动上下文
→ 重新注入确定性经营状态
→ 继续对话
```

重新注入的状态包括：

- 当前服务与订单；
- 当前排期和产能；
- 当前瓶颈和实验；
- 已确认与被拒绝的经营判断；
- 未完成任务；
- 与当前对象相关的客户和反馈。

自然语言摘要不能替代数据库中的确定性状态。

### 16.6 Context Builder

模型请求按顺序组装：

```text
1. System Policy
2. 当前工作流和允许动作
3. 当前服务/订单/客户/实验
4. 已确认且相关的长期记忆
5. 按需召回的经营事件与证据
6. 最近对话或会话摘要
7. 当前用户输入
8. 结构化输出协议
```

不发送与当前任务无关的完整历史。

### 16.7 记忆写入

```text
业务事件或用户输入
→ 提取候选事实
→ Schema 校验
→ 冲突和重复检测
→ 按风险请求用户确认
→ 写入事件与记忆
→ 更新当前有效状态
```

AI 不能直接覆盖用户档案或经营事实。

### 16.8 技术组件

```text
ActivityEventStore
ConversationStore
MemoryStore
MemoryExtractor
MemoryConflictResolver
MemoryRetriever
ConversationCompactor
TokenBudgetManager
ContextBuilder
DeepSeekProvider
InsightEngine
```

### 16.9 洞察生成边界

AI 洞察必须：

- 引用相关数据；
- 区分事实、推断和未知；
- 说明样本量；
- 不制造虚假精确概率；
- 不把相关性描述为因果；
- 提供其他可能解释；
- 优先提出可验证的小实验。

## 17. MVP 核心数据模型

### 17.1 主要实体

```text
users
services
leads
customers
orders
schedule_blocks
feedback
insights
experiments
assets
activity_events
conversations
messages
memories
ai_runs
```

### 17.2 关键关系

```text
User
├── Services
├── Leads ──→ Customer ──→ Orders
│                              ├── ScheduleBlocks
│                              └── Feedback
├── ActivityEvents
├── Insights ──→ Experiments
├── Assets
├── Conversations ──→ Messages
└── Memories
```

### 17.3 最小字段要求

详细字段在《个人经营核心工作流协议 v0.1》中定义。PRD 层要求：

- 所有业务对象拥有 `user_id`、状态和时间字段；
- 阶段变化写入 `activity_events`；
- 洞察证据保存对象类型与 ID；
- 资产保存来源订单或事件；
- AI 运行保存工作流、模型、Prompt 版本、Token、耗时和状态；
- 记忆保存来源、事实状态、有效期和确认信息；
- 客户敏感信息不得进入不必要的 AI 上下文。

### 17.4 数据安全

- 用户数据按 `user_id` 隔离；
- API Key 只存在服务端；
- 所有暴露给客户端的表启用行级权限；
- 用户可删除和导出数据；
- AI 日志默认不长期保存完整敏感 Prompt；
- 客户原话进入模型前应支持脱敏策略。

## 18. 成功指标

### 18.1 激活指标

- 创建首个服务；
- 创建首个真实订单；
- 创建首周排期；
- 完成首个订单闭环；
- 完成首次回访；
- 获得首条有效经营观察。

### 18.2 使用指标

- 每周更新客户阶段的用户数；
- 每周管理真实订单的用户数；
- 每周查看排期的用户数；
- 每周完成回访的用户数；
- 每周采纳经营实验的用户数；
- 每周沉淀流程或资产的用户数。

### 18.3 质量指标

- 洞察准确/拒绝比例；
- 建议采纳率；
- 建议产生可记录结果的比例；
- 用户修改 AI 提取结果的比例；
- 无依据洞察率；
- 创建一条线索和订单所需时间；
- 因记录成本而中断的比例。

### 18.4 长期结果指标

- 流失原因可识别率；
- 回访完成率；
- 超期率；
- 平均实际投入时间；
- 复购和转介绍记录率；
- 订单单位时间收入；
- 被稳定复用的经营资产数量；
- 从内部资产发展出的新产品数量。

### 18.5 北极星指标

**每周完成至少一次真实经营闭环，并基于结果采取一次优化行动的活跃用户数。**

不使用 AI 对话次数、内容生成量、知识库数量、Agent 数量或仪表盘浏览次数作为北极星指标。

## 19. MVP 验收标准

### 19.1 经营管理

- 创建服务并设置价格、交期和工作量；
- 记录线索并推动阶段；
- 将线索转化为客户和订单；
- 查看进行中和历史订单；
- 记录流失、取消和未知原因。

### 19.2 排期与产能

- 在周视图安排订单工作；
- 计算已占用、缓冲和剩余时间；
- 创建订单时提示冲突；
- 展示新订单加入后的影响；
- 设置不可工作时间和缓冲。

### 19.3 交付与反馈

- 记录订单实际投入；
- 标记交付完成；
- 创建待回访任务；
- 记录反馈和客户行动状态；
- 无反馈不会默认满意。

### 19.4 诊断与资产

- 基于真实数据生成一条可追溯观察；
- 区分事实、假设和未知；
- 用户可以采纳、忽略或纠正；
- 识别至少一种重复工作；
- 用户可以保存为清单或流程；
- AI 失败不影响基础经营功能。

### 19.5 体验

- 用户不从聊天开始；
- 新建线索不超过 30 秒；
- 更新阶段不超过两次操作；
- 一个页面能判断本周是否还能接单；
- 页面不使用虚构经营数据；
- 用户能理解 Bee 为何给出观察。

## 21. 主要风险与对策

| 风险 | 对策 |
|---|---|
| 退化为聊天机器人 | 真实业务对象作为信息架构，聊天不作为首页 |
| 与 Moxie 功能同质化 | 强调诊断、实验和资产沉淀，不只做管理 |
| 做成复杂 CRM | 首版不做合同、支付、门户、复杂自动化 |
| 用户不愿记录 | 记录嵌入订单、排期和交付动作 |
| 数据少却强行分析 | 展示样本量，只提出待验证问题 |
| 洞察泛化 | 每条洞察引用具体对象和事件 |
| 排期退化为日历 | 连接服务耗时、修改缓冲和真实产能 |
| 无反馈被误判满意 | 明确区分未回访、未回复、未行动和满意 |
| 自动生成无用知识 | 重复出现并经确认后才沉淀 |
| AI 影响基础可靠性 | 核心状态和计算使用确定性逻辑 |
| 隐私风险 | 数据隔离、可删除、可导出、上下文可控 |
| 范围持续膨胀 | MVP 只完成订单、排期、反馈和一条洞察 |

## 22. 待确认事项

1. 第一批种子用户是否确定聚焦简历修改、求职辅导和专业咨询；
2. 首版是否只支持个人账户；
3. 排期只做内部安排，还是包含客户预约链接；
4. 是否首版支持急单价格和急单名额；
5. 用户是否愿意录入最近 3–5 个历史订单；
6. 反馈首版是手动记录，还是生成客户填写链接；
7. 首版经营洞察是否确定“规则引擎为主，AI 为辅”；
8. 内容模块只记录来源，还是需要轻量内容管理；
9. 每个服务是否必须设置标准工作量和修改缓冲；
10. 资产首版只支持清单和 SOP，还是包括知识条目；
11. Bee 首版采用视觉角色，还是仅使用语言和提示标识；
12. 技术部署是否继续使用现有 Sites/vinext，还是重新选择完整应用栈。

## 23. 下一份设计文档

PRD 确认后，优先产出《个人经营核心工作流协议 v0.1》，不继续编写聊天 Prompt。

该文档需要定义：

### A. 服务与订单

- 服务字段；
- 状态切换条件；
- 异常状态；
- 实际耗时记录。

### B. 线索与客户

- 最小字段；
- 看板阶段；
- 流失原因枚举；
- 下一步动作规则。

### C. 排期与产能

- 用户可用时间；
- 服务标准耗时；
- 准备和修改缓冲；
- 超载判断；
- 新订单模拟。

### D. 反馈闭环

- 回访问题；
- 反馈状态；
- 客户行动状态；
- 复购与转介绍。

### E. 首批五类经营洞察

1. 排期即将超载；
2. 多名客户因交期流失；
3. 报价后集中流失；
4. 订单完成但长期无反馈；
5. 同一问题或步骤重复出现。

### F. 首版原型

1. 今日经营首页；
2. 客户与线索看板；
3. 排期与产能；
4. 订单工作区；
5. 经营观察详情；
6. 流程资产详情。

首版开发判断标准：

> **即使暂时关闭 AI，用户是否仍愿意使用 BeWater 管理真实订单、客户和排期；当数据积累后，AI 是否能给出用户不容易发现、但有明确依据的经营观察。**
